# Plan: ADT-Bench - Agent-First ABAP Scenario Runner

**Status:** Draft v0.2 (revised after first round of feedback)
**Audience:** project maintainers, contributors, and agent-runtime implementers
**Primary goal:** benchmark a pure agent that receives a scenario prompt, skills, MCP configuration, and optional workflow orchestration, then returns a structured result.

> **Note on revision:** the previous draft focused on building connector packages and normalizing ABAP tool APIs. This revision is **agent-first**: MCP is the tool boundary, the benchmark just configures MCP servers (no custom wrappers), scenarios describe acceptance criteria (not command sequences), and telemetry is optional. The benchmark's job is to run an agent, capture the result, and evaluate it.

---

## 1. Executive summary

ADT-Bench should be an **agent-first benchmark runner** for ABAP development scenarios. The benchmark must not become a connector-development project. Its job is to prepare a scenario, provide domain skills, configure MCP servers, run an agent, capture the transcript and final answer, and evaluate whether the result satisfies the scenario.

Mastra Code is the first supported runtime because it is TypeScript-friendly, can be configured with skills and MCP servers, and can live inside a TypeScript/Nx workflow. However, Mastra Code is not the permanent architecture boundary. The benchmark should allow other agents later, such as Claude Code, Codex CLI, Gemini CLI, Cursor, or any agent process that can consume a prompt and produce an answer.

The target shape is:

```txt
scenario prompt
+ skills
+ MCP server configuration
+ agent instructions
+ optional TypeScript workflow
-> agent run
-> structured result JSON
-> evaluator
-> report
```

The target shape is **not**:

```txt
scenario
+ custom ABAP adapters
+ normalized tool wrappers
+ connector-specific error mapping
-> benchmark result
```

MCP is the connector boundary. Existing MCP servers or CLIs may be used, but v1 should avoid wrapping them into custom TypeScript tool packages unless a thin runner shim is absolutely required to execute the agent.

---

## 2. Revised goal

Build an SDD/TDD-first, AI-first, TypeScript-based benchmark runner that executes ABAP scenarios through a pure agent loop.

The runner provides:

- scenario prompt
- domain skills
- agent instructions
- MCP server configuration
- optional TypeScript workflow orchestration
- result parsing
- evaluation and reporting

The runner does **not** implement ADT connectors, normalize ABAP tool APIs, wrap every CLI command as a Mastra tool, or create new MCP servers in v1.

### One-sentence product definition

ADT-Bench runs an agent against ABAP scenarios with configured skills and MCP servers, then measures whether the agent produced the required result.

---

## 3. Non-goals

The following are explicitly out of scope for v1:

1. Building ABAP ADT connectors.
2. Creating TypeScript wrappers around `adt-cli`, `arc-1`, or `vscode_abap_remote_fs` as benchmark-owned tool packages.
3. Normalizing error envelopes across tool providers.
4. Forcing all tools into a canonical command set.
5. Comparing connector internals as the primary benchmark objective.
6. Requiring `adt_http_calls` for every run.
7. Requiring token, cost, or step metrics from every agent runtime.
8. Creating upstream pull requests to external projects.
9. Shipping a static website in v1.
10. Running against live BTP as the default CI mode.

Some of these may become optional future work, but they should not shape the v1 architecture.

---

## 4. Key design principles

### 4.1 Agent-first, not connector-first

The primary unit under test is the agent behavior: can it read the scenario, use the available skills and MCP tools, make progress, validate its work, and return a structured answer?

### 4.2 MCP is the tool boundary

MCP servers expose tools, schemas, and results. ADT-Bench should configure MCP servers and observe agent usage where possible. It should not reimplement or normalize MCP server behavior unless the benchmark is explicitly testing a compatibility layer.

### 4.3 Runtime-agnostic runner interface

Mastra Code is the first runtime, not the only runtime. The core package should define a small `AgentRunner` interface that can later be implemented by other agents.

### 4.4 Scenario-driven evaluation

Scenarios define goals, constraints, expected result schema, and evaluation rules. They should not prescribe an exact sequence of connector operations unless the scenario is explicitly about process compliance.

### 4.5 Optional telemetry

Different agents expose different telemetry. Duration, final result, outcome, and transcript are mandatory. Tool-call counts, tokens, costs, and ADT HTTP stats are optional.

### 4.6 SDD/TDD discipline

Specs and tests come before implementation. The benchmark should test its own scenario parsing, prompt building, result parsing, evaluator rules, and runner contracts.

### Removed from the previous shape

The v1 repo should not contain these packages:


Those packages represent connector or adapter work. The agent runner may execute Mastra Code with a prepared `.mastracode/mcp.json`, but it should not translate ABAP tools into benchmark-owned wrappers.

## 6. Runtime model

### 6.1 AgentRunner interface

```ts
export interface AgentRunner {
  id: string;

  prepare(input: AgentPrepareInput): Promise<void>;

  run(input: AgentRunInput): Promise<AgentRunResult>;
}

export type AgentPrepareInput = {
  workspaceDir: string;
  agentConfigDir: string;
  skillsDir: string;
  mcpConfigPath: string;
  instructionsPath?: string;
};

export type AgentRunInput = {
  runId: string;
  scenarioId: string;
  prompt: string;
  timeoutMs: number;
  env?: Record<string, string>;
};

export type AgentRunResult = {
  runId: string;
  agentId: string;
  scenarioId: string;
  startedAt: string;
  finishedAt: string;
  durationMs: number;
  exitCode?: number;
  finalText: string;
  parsedResult?: ScenarioResult;
  transcriptPath?: string;
  metrics?: OptionalRunMetrics;
  error?: string;
};
```

This interface deliberately knows nothing about ABAP, ADT, `adt-cli`, `arc-1`, or `vscode_abap_remote_fs`.

### 6.2 Mastra Code runner

The first concrete runner should:

1. Create a temporary workspace for the scenario run.
2. Copy or generate `AGENTS.md`.
3. Copy relevant skills into `.mastracode/skills/`.
4. Write `.mastracode/mcp.json` from the selected benchmark config.
5. Optionally write `.mastracode/hooks.json` for logging and guardrails.
6. Execute the agent with the built prompt.
7. Capture stdout/stderr, transcript, final answer, and optional telemetry.
8. Return an `AgentRunResult`.

The runner should treat Mastra Code as an agent process/runtime, not as a place to rebuild connector APIs.

## 7. Scenario contract

Scenarios are markdown files with frontmatter and a required final-result contract. They describe the task and the acceptance criteria. They should not force tool-call details unless the task explicitly needs that.

Example:

```md
---
id: create-class-hello
title: Create ABAP hello class
difficulty: easy
required_mcp_servers:
  - abap
required_skills:
  - abap-workflow
  - abap-test-loop
timeout_ms: 300000
---

## Goal

Create class `ZCL_BENCH_HELLO` with method `SAY_HELLO` returning `Hello, world!`.

## Constraints

- Use the configured ABAP MCP tools.
- Do not assume the object already exists.
- Validate the final result through available checks or tests.
- Return only the expected final JSON.

## Acceptance criteria

- Class `ZCL_BENCH_HELLO` exists.
- Method `SAY_HELLO` exists.
- The method returns `Hello, world!`.
- The class is activated or otherwise reported as ready.
- The final answer contains evidence.

## Expected final response

Return only JSON matching the scenario result schema.
```

### Scenario frontmatter schema

```ts
export type ScenarioFrontmatter = {
  id: string;
  title: string;
  difficulty: 'easy' | 'medium' | 'hard';
  required_mcp_servers: string[];
  required_skills?: string[];
  timeout_ms?: number;
  tags?: string[];
  evaluator?: {
    type: 'rule' | 'agent' | 'hybrid';
    rules?: string[];
  };
};
```

## 8. Skills

Skills are benchmark-owned domain instructions. They teach the agent the ABAP workflow, testing loop, and evaluation expectations. They should remain tool-agnostic.

Suggested v1 skills:

| Skill | Purpose |
|---|---|
| `abap-workflow` | Standard ABAP object workflow: discover, create or edit, check, activate, validate. |
| `abap-test-loop` | Test-driven loop: inspect, change, check syntax, run tests, diagnose, fix. |
| `abap-result-contract` | How to return strict scenario JSON with evidence and no extra prose. |
| `abap-mock-usage` | Differences and deterministic behavior when using the mock ADT server. |

Skills should not say "call tool X" unless that skill is specifically for one runtime or one MCP server. The default skill set should describe the work, not the API.

## 9. MCP configuration

Each run selects an MCP profile. The profile is copied into the agent workspace as `.mastracode/mcp.json` for the Mastra Code runner.

Example profile:

```json
{
  "mcpServers": {
    "abap": {
      "command": "npx",
      "args": ["-y", "arc-1@latest", "--stdio"],
      "env": {
        "ABAP_URL": "http://127.0.0.1:8080",
        "ABAP_USER": "demo",
        "ABAP_PASSWORD": "demo"
      }
    }
  }
}
```

Profiles should live under:

```txt
agents/mastracode/profiles/mock-arc-1.mcp.json
agents/mastracode/profiles/live-arc-1.mcp.json
agents/mastracode/profiles/local-custom.mcp.json
```

The benchmark may validate that the selected profile exists and has the named MCP servers required by the scenario. It should not validate every underlying ABAP capability in v1.

## 10. Prompt builder

The prompt builder combines stable instructions with scenario-specific content.

Prompt sections:

1. Role: you are an ABAP development agent.
2. Available context: scenario id, title, goal, constraints.
3. Tool policy: use configured MCP tools, avoid unsupported assumptions.
4. Validation policy: verify through checks/tests/tool evidence where available.
5. Result policy: return only strict JSON.
6. Scenario body: original markdown content.
7. Result schema: JSON schema or TypeScript-shaped contract.

The prompt builder should not inject connector-specific adapter documentation by default. Connector-specific information belongs in MCP server docs or optional per-profile notes.

## 11. Result schema

Mandatory result:

```ts
export type ScenarioResult = {
  scenario_id: string;
  status: 'pass' | 'fail' | 'partial';
  summary: string;
  evidence: Evidence[];
  changed_objects: string[];
  errors: string[];
};

export type Evidence = {
  kind:
    | 'object'
    | 'source'
    | 'activation'
    | 'syntax_check'
    | 'test'
    | 'diagnostic'
    | 'tool_result'
    | 'other';
  value: string;
};
```

The agent must return this JSON as its final answer. The evaluator parses it and then scores against scenario-specific rules.

---

## 12. Run result schema

Core run result:

```ts
export type CoreRunResult = {
  run_id: string;
  agent_id: string;
  scenario_id: string;
  status: 'pass' | 'fail' | 'partial' | 'timeout' | 'error';
  started_at: string;
  finished_at: string;
  duration_ms: number;
  final_result: ScenarioResult | null;
  transcript_path?: string;
  errors: string[];
};
```

Optional metrics:

```ts
export type OptionalRunMetrics = {
  tool_calls?: {
    total?: number;
    by_tool?: Record<string, number>;
  };
  tokens?: {
    input?: number;
    output?: number;
    cache_read?: number;
    cache_write?: number;
  };
  cost_usd?: number;
  steps?: number;
  mcp_servers?: string[];
  adt_http_calls?: {
    total?: number;
    by_endpoint?: Record<string, number>;
  };
};
```

This schema keeps the benchmark portable. A process-only agent might only provide stdout and duration. A deeply integrated runner might provide full tokens, costs, and tool-call events.

## 13. Evaluator

The evaluator should be deterministic in v1.

### 13.1 Evaluation inputs

- scenario metadata
- scenario acceptance criteria
- parsed final JSON
- transcript, if available
- optional mock server state
- optional MCP/tool telemetry

### 13.2 Evaluation modes

| Mode | v1 status | Purpose |
|---|---|---|
| Rule-based | Required | Deterministic pass/fail against JSON and known fixtures. |
| Agent-based | Future | Use a second evaluator agent for qualitative grading. |
| Hybrid | Future | Rule gate first, evaluator agent second. |

### 13.3 Example rule set

For `create-class-hello`:

1. Final JSON parses.
2. `scenario_id` equals `create-class-hello`.
3. `status` is `pass` or `partial`.
4. `changed_objects` includes `ZCL_BENCH_HELLO`.
5. Evidence includes at least one activation, syntax check, or test item.
6. No fatal errors are reported.
7. Optional mock inspection confirms the class/method state.

The evaluator should record both the agent's self-reported status and the benchmark's judged status.

## 14. Mock ADT server

A mock ADT server is useful for deterministic CI, but it should be treated as an optional benchmark fixture, not the center of the architecture.

V1 responsibilities:

- provide deterministic ABAP-like state for smoke scenarios
- support reset between runs
- expose optional inspection endpoints for the evaluator
- expose optional HTTP call stats if available

The mock does not need to perfectly emulate every ADT endpoint in v1. It only needs enough behavior to support smoke scenarios and deterministic evaluator checks.

Suggested v1 mock endpoints:

```txt
POST /__mock/reset
GET  /__mock/state
GET  /__mock/stats
```

ABAP-facing endpoints can be added only as needed by the MCP server used in the smoke profile.

## 16. V1 deliverables

V1 should be a small end-to-end proof, not a full benchmark arena.

1. Nx + pnpm + TypeScript repo skeleton.
2. `packages/agent-runner` with shared runner/result contracts.
3. `packages/runner-mastracode` with the first concrete runner.
4. `packages/scenarios` with markdown loader and schema validation.
5. Two scenarios:
   - `create-class-hello`
   - `read-class-source`
6. `packages/skills` with local `SKILL.md` files.
7. `packages/prompt-builder` for scenario prompts and result schema injection.
8. `packages/evaluator` with deterministic rule evaluation.
9. One MCP profile for a mock or disposable ABAP backend.
10. Optional mock ADT server sufficient for the smoke scenario.
11. `results/<run-id>/result.json` and `results/summary.json`.
12. Console report.
13. README and reproducing guide.

### V1 success criterion

A contributor can run one command and see a complete agent run:

```bash
pnpm bench:smoke
```

The command produces:

```txt
results/<run-id>/transcript.json
results/<run-id>/result.json
results/summary.json
```

The console report shows whether the agent satisfied the scenario.

## 18. SDD/TDD gates

`pnpm verify` should run:

1. `pnpm spec-check`
2. `pnpm typecheck`
3. `pnpm lint`
4. `pnpm test`
5. `pnpm bench:smoke`

Minimum tests:

- scenario frontmatter validation
- prompt builder snapshot tests
- final JSON parser tests
- evaluator rule tests
- Mastra runner command construction tests
- result writer tests
- smoke scenario test against mock or fixture mode

The implementation should be allowed to evolve, but the contracts must stay stable.

## 19. Security and safety

A pure-agent benchmark can call powerful tools. The benchmark should default to safe execution.

V1 safety defaults:

- use mock or disposable ABAP systems
- isolate each run in a temporary workspace
- avoid persistent credentials in repo files
- pass credentials via environment variables
- record which MCP servers were configured
- deny unknown MCP profiles in CI
- set run timeouts
- capture transcripts for audit
- avoid autonomous upstream PRs or public writes

Sensitive operations should require an explicit profile and an explicit command flag, for example:

```bash
pnpm bench:run --profile live-btp --allow-live-system
```

## 20. Migration from the old plan

The old plan should be reframed as follows:

| Old framing | New framing |
|---|---|
| Compare three ABAP tool surfaces as the main variable. | Run a pure agent with scenario, skills, MCP config, and evaluate result. |
| `tools-adt-cli`, `tools-arc-1`, `tools-abapfs` packages. | No connector packages in v1. Use MCP profiles and agent config. |
| Canonical command set per scenario. | Scenario acceptance criteria and final result contract. |
| Error normalization across adapters. | Preserve tool behavior; evaluate final result and evidence. |
| Mandatory `adt_http_calls`. | Optional telemetry when mock/proxy exposes it. |
| Mastra as the benchmark's fixed loop. | Mastra Code as first runtime behind `AgentRunner`. |
| Full matrix benchmark in v1. | One end-to-end smoke path first. |

## 21. Recommended first milestone

Milestone 1: **Mastra Code smoke runner**

Scope:

1. Create repo skeleton.
2. Add scenario schema and one scenario.
3. Add two skills.
4. Add Mastra Code runner that writes `.mastracode/mcp.json`.
5. Add prompt builder and strict result schema.
6. Add deterministic evaluator.
7. Run one smoke scenario against one configured MCP profile.
8. Emit `result.json`, `transcript.json`, and `summary.json`.

Exit criteria:

- no custom ADT adapter code exists
- the scenario can run through an agent
- the final result is parsed and evaluated
- docs explain how to add a scenario, skill, MCP profile, and agent runner

## 22. Open questions

These should be resolved early, but they do not block the architecture:

1. Should the Mastra Code runner use a public programmatic API or execute the CLI process?
2. Which MCP server should be the default smoke profile?
3. Should the smoke scenario use a mock server, a fake MCP server, or a disposable ABAP backend?
4. What is the minimum transcript format that works across runtimes?
5. Should evaluator rules inspect only final JSON in v1, or also inspect mock state?
6. How strict should the final-answer JSON parser be?

Recommended defaults:

- Start with CLI execution if the programmatic API is unstable.
- Use the simplest MCP profile that can complete one scenario.
- Use mock or fixture mode for CI.
- Parse final JSON strictly, but store raw final text for debugging.
- Keep telemetry optional.

---

## 23. Bottom line

ADT-Bench should prove this loop first:

```txt
agent + skills + MCP + scenario prompt -> structured result -> evaluator
```

Everything else is secondary. The v1 benchmark should stay small, deterministic, and runtime-agnostic. Mastra Code is a good first implementation because it is TypeScript-friendly and supports the agent features needed for this shape, but the architecture should make it replaceable from day one.
