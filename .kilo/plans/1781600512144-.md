# Plan: ADT-Bench — AI-driven ABAP/MCP Comparison Framework

## Goal (recap)

An SDD + TDD-first, AI-first, open-source benchmark arena that runs the **same agent loop** (mastracode / @mastra/core) against the **same ABAP scenarios** (markdown Given/When/Then) using **three different tool surfaces** as the only variable:

1. **`abapify/adt-cli`** (TypeScript, npm) — CLI exposed via `npx @abapify/adt-cli` + skills
2. **`marianfoo/arc-1`** (TypeScript, MCP) — stdio MCP server
3. **`marcellourbani/vscode_abap_remote_fs`** (TypeScript, embedded MCP) — same author's stack as `abap-adt-api`

Captured per (scenario × tool × run): pass/fail, tool-call count, tokens in/out, wall time, USD cost, #steps. JSON output. v1: console. v2: static website.

All runs hit a **mock ADT server** (no BTP key needed in CI). Same swap point accepts a real BTP service key in production.

---

## Constraints honored (from user)

- **TypeScript** everywhere — drop Inspect (Python). Roll our own lightweight harness, or use a TS-native framework.
- **Nx monorepo** — single repo, multiple packages, shared TS config, shared types.
- **`mastracode`** as the agent — its `createMastraCode()` is embeddable, headless, instrumented, hook-able.
- **Skills can be rebuilt locally** — no upstream dependency on `abapify/skills` in v1. We author them inside the bench repo; later migrate to shared.
- **3 tools** in v1: `abapify/adt-cli`, `arc-1`, `vscode_abap_remote_fs`.
- **Mock ADT server** first; BTP key swap later via `BTP_SERVICE_KEY` env.
- **No autonomous PRs to public upstream repos.** All work goes into a **new repo** under the `abapify` org. Drafting a PR to `arc-1` is a separate, explicit future request.
- **SDD / TDD / AI-first**: specs before code, tests before impl, agent-first design.

### Key design decisions (rationalized)

| Decision | Choice | Why |
|---|---|---|
| Monorepo tool | **Nx 20+** with pnpm workspaces | User-requested. Nx gives us task graph, affected-only CI, generators. |
| Agent loop | **`createMastraCode()` from `mastracode`** | User-requested. Embeddable, hook-able, LibSQL token storage, YOLO mode, `@mastra/mcp` first-class. |
| MCP client | **`@mastra/mcp`** (Mastra's MCP client) | Already bundled; same loop handles all 3 tools uniformly. |
| CLI invocation | **`execa`** in a Mastra "bash-style" tool wrapper | `adt-cli` commands are subcommands — we generate one Mastra tool per command. |
| Mock ADT server | **Express 4 + xmlbuilder2** (TS) | Same language as everything else; matches the research spec. |
| Scenarios | **Markdown files + Zod schema in `scenarios.ts`** | Given/When/Then is markdown. Validation is Zod. |
| Metrics | **Custom collector + Mastra hooks** | Tokens from Mastra. Tool calls from hook. Wall time from `performance.now()`. |
| Results | **JSONL append-only, one file per run, committed to a `results/` branch** | Trivial to render; git-diffable. |
| Testing | **Vitest** (unit + integration) + **`@microsoft/tui-test`** if needed | TS-native, fast, Nx-friendly. |
| Linting | **ESLint strict + tsgo (typecheck)** | Project default. |
| Spec/SDD | **`docs/specs/*.md` per package, required-before-code** | Gate. `pnpm spec-check` fails if a package's `docs/specs/*.md` is older than its `src/`. |

### Data flow (per run)

```
[ LLM provider  ] ─┘            │

                                │
                  ┌─────────────┼─────────────┐
                  ▼             ▼             ▼

                  └─────────────┴─────────────┘

                                │
                                ▼

```

### Metrics JSON contract (per run)

```ts
type RunResult = {
  run_id: string;                  // ulid
  started_at: string;              // ISO
  finished_at: string;             // ISO
  duration_ms: number;
  scenario: {
    id: string; title: string;
    difficulty: 'easy'|'medium'|'hard';
    optimization: 'none' | 'method-level-ok';   // see §Scenarios
  };
  tool_under_test: {
    id: 'adt-cli' | 'arc-1' | 'abapfs';
    variant: 'cli' | 'mcp-stdio' | 'mcp-http' | 'stub';  // abapfs has stub|mcp
    version: string;             // resolved at runtime (e.g. arc-1@0.9.17)
    transport: 'cli' | 'mcp-stdio';
  };
  llm: { provider: string; model: string; seed: number };
  outcome: 'pass'|'fail'|'timeout'|'budget_exceeded'|'error';
  score: { primary: number; details: Record<string, number> };  // 0..1
  metrics: {
    tool_calls:    { total: number; by_tool: Record<string, number> };  // LLM-visible
    adt_http_calls:{ total: number; by_endpoint: Record<string, number> };  // mock-reported
    tokens:        { input: number; output: number; cache_read: number; cache_write: number };
    cost_usd:      number;
    steps:         number;          // LLM turns
    bytes_in:      number;          // tool input sizes summed
    bytes_out:     number;          // tool output sizes summed
  };
  transcript_path: string;         // transcript.json
  errors: string[];
};

type TranscriptEntry = {
  type: 'user' | 'assistant' | 'tool';
  toolName?: string;
  content: string;
  usage?: { input_tokens: number; output_tokens: number };
  timestamp: string;                 // ISO
};
```

### Why we separate `tool_calls` from `adt_http_calls`

`arc-1` collapses multiple ADT operations into one MCP call by design; `vscode_abap_remote_fs` exposes 39 fine-grained tools; `adt-cli` is 1:1 with REST endpoints. To make a fair comparison we record **both**:

- `tool_calls` — what the LLM sees. Measures prompt-tool efficiency and tool-design quality.
- `adt_http_calls` — what crosses the wire to the mock. Measures underlying network/API chatter. Aggregated by the mock server's `/__mock/stats` and polled at end-of-run.

Same outcome may show "arc-1 wins on `tool_calls` but `abapfs` wins on `adt_http_calls`" — that's the hypothesis the framework is designed to test.

## Scenarios (v1, 6 tasks)

Each is a markdown file `scenarios/<id>.md` with `## Given / ## When / ## Then` + Zod-validated metadata in frontmatter. Frontmatter also carries an `optimization` flag controlling whether method-level / compressed-context operations count as bonus (see below).

| ID | Title | Difficulty | Optimization | Validates |
|---|---|---|---|---|
| `create-class-hello` | Create `ZCL_BENCH_HELLO` with `say_hello( )->string` returning `'Hello, world!'`, activate, run AUnit. | easy | `none` | create, write, activate, aunit, CSRF, lock/unlock |
| `read-class-source` | Find the existing `ZCL_BENCH_FIXTURE_OK`, read its source, print the class name. | easy | `none` | search, read |
| `syntax-error-recovery` | Write invalid ABAP, run checkruns, interpret the error, fix it, re-check. | medium | `none` | checkruns error parsing, self-correction |
| `abapunit-failure-diagnose` | Read `ZCL_BENCH_FIXTURE_FAIL_AUNIT`, run AUnit, parse the JUnit result, identify the failing assertion. | medium | `none` | aunit, junit XML parse |
| `create-transport-zpkg` | Create class in `ZPKG_BENCH` package, run transportchecks, link the created TR. | medium | `none` | transportchecks, transport awareness |
| `bdef-scaffold-rap` | Create a behavior definition for `ZCL_BENCH_HELLO` with `for create` and `for update delete`. | hard | `method-level-ok` | BDEF namespace, RAP preflight |

### Per-tool "allowed command set" (encoded in skill metadata)

To keep the search space consistent across very different tool surfaces, each scenario's `## When` section names a minimal canonical command set, derived from `adt-cli --help` and the MCP tool lists. All three adapter packages expose exactly these operations (the MCP wrappers may bundle them — that's fine, but the count of *distinct LLM tool calls* is the metric we measure):

- `create-class-hello`: `search`, `class create` / `create_object`, `source put` / `set_source`, `activate` / `activate_object`, `aunit run` / `run_unit_tests`
- `read-class-source`: `search`, `source get` / `get_source`
- `syntax-error-recovery`: `source put`, `checkruns` / `check_syntax` (×N)
- `abapunit-failure-diagnose`: `source get`, `aunit run` (×N), `aunit results` / `get_test_results`
- `create-transport-zpkg`: `transport check` / `cts_get_transport`, `class create`, `source put`, `activate`
- `bdef-scaffold-rap`: `bdef create` / `create_behavior_definition`, `source put`, `activate`

### `optimization` flag and arc-1's intent-based tools

Arc-1 collapses many ADT operations into single high-level calls (`SAPRead` with `method=…`, `SAPContext` with `action=deps` etc.). These are genuine wins for the LLM but would be unfair on scenarios that count "must call class create" as a step. Rule:

- `optimization: 'none'` — agent must call each canonical command at least once; no credit for fewer.
- `optimization: 'method-level-ok'` — arc-1 may bundle read/write at method level; credit is the secondary `metrics.tool_calls.total` only.

This is encoded in the scenario frontmatter and consumed by the harness's scoring logic.

## Skills (local, rebuildable)

Authored under `packages/skills/.agents/skills/<name>/SKILL.md`, agentskills.io format. 4 skills in v1:

- `abap-workflow` — teaches the agent the standard lock → write → unlock → activate order, CSRF bootstrap, error-recovery patterns.
- `abap-test-loop` — when the task is "make tests pass", the canonical cycle (read source → write → checkrun → aunit → parse junit → fix).
- `abap-mock-usage` — when the mock server is in use, quirks to expect (`!@MOCK_AUNIT_FAIL` markers, deterministic runIds, no real transport).
- `abap-eval-grader` — used by the **evaluator agent** (second agent) to score a run; reads the transcript, walks the scenario's Then clauses, emits a per-clause pass/fail.

All four are loaded by the harness as `system_message` fragments into the Mastra agent at start. They are tool-agnostic by design — they describe the *work*, not the *API*.

## Mock ADT Server (`packages/mock-adt-server`)

Implements the 16-endpoint minimum set from the research spec (mock_adt_spec.md):
- discovery, search (RIS quickSearch GET), class CRUD, lock/unlock, activation, checkruns, abapunit (start/poll/results), transportchecks, packages
- CSRF token flow (`X-CSRF-Token: Fetch` on GET → token in response; required on POST/PUT)
- Fixtures loader: reads `fixtures/<scenario-id>/*.json` per-scenario namespace; falls back to `fixtures/_default/`
- `/__mock/reset` (admin-key gated) and `/__mock/stats` (returns `adt_http_calls.by_endpoint` + per-route call counts)
- Determinism knobs (request header driven):
  - `X-Mock-Delay-Ms: <int>` — server-side artificial latency
  - `X-Mock-Aunit-Outcome: pass|fail` — overrides the `!@MOCK_AUNIT_FAIL` source marker
  - `X-Mock-Error-Mode: network|server|csrf|lock` — scriptable failure patterns for robustness tests (e.g. `csrf` returns 403 on first POST, allowing tests of CSRF recovery)
- Content types match SAP exactly: `application/vnd.sap.adt.oo.classes.v2+xml`, `application/vnd.sap.adt.checkmessages+xml`, `application/vnd.sap.adt.api.junit.run-result.v1+xml`, etc.
- XML payloads mirror `@abapify/adt-fixtures` shapes (class descriptor, checkmessages, JUnit) so the mock is a faithful drop-in for tests of all three adapters

Tested with **Vitest + supertest** + a captured-response fixture set mirroring `@abapify/adt-fixtures`.

## Tool Adapters

All three adapter packages export the **same** `ToolBundle` interface (see below) so the harness is surface-agnostic. They differ in transport, granularity, and quirks — and those differences are deliberately *visible* in `metrics` so the comparison is data-driven, not anecdotal.

### v1 surface strategy (locked)

| Tool | v1 surface | v1.1 plan |
|---|---|---|
| `abapify/adt-cli` | **CLI** via `npx @abapify/adt-cli` + skills (zod-validated, `--json` outputs) | Add `mcp-stdio` variant for `abapify MCP vs arc-1 MCP` apples-to-apples |
| `marianfoo/arc-1` | **MCP stdio** via `npx arc-1@latest --stdio` (12 intent-based tools) | Add `mcp-http` variant (Streamable HTTP, session-scoped) |
| `vscode_abap_remote_fs` | **Defer** — only `abapfs-stub` is built in v1.1, no v1 work | v1.1: `abapfs-stub` (TS module using `abap-adt-api` directly, same tool names) → v1.2: `abapfs-mcp` via `code --headless` + xvfb |

Rationale: in v1 we want a clean two-tool comparison (CLI vs MCP, intent-based vs 1:1) that yields immediate data. Adding the third tool in v1.1 lets us also fix the `vscode_abap_remote_fs` VS Code host problem as a separate, scoped milestone.

### `packages/tools-adt-cli` (CLI + skills, v1)

- Uses **`execa`** to spawn `npx @abapify/adt-cli`
- Generates **one Mastra tool per `adt` subcommand** at startup by running `adt --help` and parsing (commands discovered at adapter-init time; pinned via lockfile in v1.1)
- Each tool:
  - Validates inputs with Zod (mirrors the CLI's own Zod schemas)
  - Adds `--json` flag where supported for structured output
  - Maps `exitCode` to a normalized error envelope: `{ kind: 'ok'|'error'|'not_found'|'auth'|'transport_required'|'csfr'|'lock_conflict', message, retriable, raw }`
  - Exit codes standardized: `0` → `ok`, `1` → `error`, `10` → `not_found`
- Auth: `BTP_SERVICE_KEY` env or `--user demo --password demo --url http://127.0.0.1:8080` against the mock
- Skills `abap-workflow`, `abap-test-loop` loaded as `systemFragments`

### `packages/tools-arc-1` (MCP stdio, v1)

- Uses **`@mastra/mcp`** to spawn `npx arc-1@latest --url <mock> --user demo --password demo --stdio`
- MCP tool list auto-discovered at startup; one Mastra tool per MCP tool, **1:1 mapping** (MCP `inputSchema` → Mastra Zod)
- **Error normalization layer** (critical, because arc-1 deliberately hides SAP XML internals):
  - All tool results are unwrapped to `{ ok: boolean, data?: unknown, error?: { kind, message, retriable, hint? } }`
  - `error.kind` is one of: `LOCKED_BY_OTHER` | `NOT_FOUND` | `AUTH_FAILED` | `INVALID_URI` | `THROTTLED` | `BUDGET_EXCEEDED` | `INTERNAL` | `TIMEOUT` (mapped from arc-1's internal codes via a translation table in the adapter)
  - This keeps the LLM-facing error surface consistent with the CLI adapter
- Skills same as CLI variant
- Known quirk surfaced in scenario scoring: arc-1 token-suppresses internal ADT errors; we record the agent's `tool_calls` so compression wins are visible but never hidden

### `packages/tools-abapfs` (deferred to v1.1)

- v1.1 ships `abapfs-stub`: a TS module that imports `abap-adt-api` directly and exposes the same 40 tool names + Zod schemas as the embedded MCP. Same `ToolBundle` interface; `variant: 'stub'`.
- v1.2 ships `abapfs-mcp`: real MCP connection with `code --headless --remote=tunnel` + `xvfb-run` (per `oisee/vibing-steampunk`'s pattern) to run the VS Code extension headlessly in CI. Same tool surface, `variant: 'mcp-http'`.
- Some `vscode_abap_remote_fs` tools are UI-only (Mermaid diagrams, webview data tables, GUI launchers) — these are **excluded from the ToolBundle** with a documented allowlist in the adapter. Only `search_*`, `get_*`, `create_*`, `replace_*`, `activate_*`, `execute_data_query`, `get_abap_diagnostics`, unit-test, transport, where-used tools are exposed.

### Common `ToolBundle` interface

```ts
export interface ToolBundle {
  id: 'adt-cli' | 'arc-1' | 'abapfs';
  variant: 'cli' | 'mcp-stdio' | 'mcp-http' | 'stub';
  version: string;             // resolved at adapter-init (e.g. via `npm view`)
  transport: 'cli' | 'mcp-stdio';
  tools: ToolDef[];            // Mastra-compatible, all errors normalized
  systemFragments: string[];   // skill markdown rendered into system_message
  // For metrics cross-checking
  capabilities: {
    canMethodLevelRead: boolean;   // arc-1: yes, adt-cli: no, abapfs: yes
    canMethodLevelWrite: boolean;  // arc-1: yes, adt-cli: no, abapfs: yes
    canBatchActivate: boolean;
    hasStructuredOutput: boolean;  // all 3 in v1
  };
}
```

## Harness (`packages/harness`)

A thin TypeScript module. ~400 LoC. No framework beyond Mastra.

```ts
// harness.run
export async function run(args: {
  scenario: Scenario;
  bundle: ToolBundle;
  llm: { provider: string; model: string; apiKey: string };
  limits: { maxSteps: number; maxTokens: number; maxCostUsd: number; timeoutMs: number };
  mockBaseUrl: string;       // http://127.0.0.1:8080
}): Promise<RunResult>
```

- Spawns/connects tools, injects skills, runs Mastra agent, subscribes to hooks:
  - `onStepFinish` → increment `steps`, capture last tool call
  - `onToolCall` → tally by tool name
  - `onUsage` → accumulate tokens
- Wall time around the whole `run()`
- Persists transcript to `results/<run-id>/transcript.json`
- Returns `RunResult`
- Exits cleanly on limits (counts as `timeout`/`budget_exceeded`)

### CLI

```bash
pnpm bench:run --tool adt-cli --scenario create-class-hello --model anthropic/claude-sonnet-4-5
pnpm bench:run --all                           # full matrix: 3 tools × 6 scenarios × N trials
pnpm bench:report                              # aggregate results/ → results/summary.json
pnpm bench:serve                               # (v2) static site on :4000
```

### Reproducibility

- `--seed` for LLM temperature=0 and per-run deterministic seeds
- `--trials N` runs each (tool, scenario) N times; aggregates mean/median/stdev
- `--parallel K` runs K concurrent (default: 1 for fairness on tokens; K for wall-time)

### LLM provisioning (provider-agnostic)

The harness resolves the LLM through environment variables — never hard-coded — so any OpenAI/Anthropic/Vertex/Ollama/LiteLLM-compatible endpoint works:

```bash
LLM_PROVIDER=anthropic        # anthropic | openai | vertex | ollama | openai-compatible
LLM_MODEL=claude-sonnet-4-5
LLM_API_KEY=sk-...            # or LLM_BASE_URL=http://localhost:11434/v1 for ollama
LLM_TEMPERATURE=0             # default 0 for benchmark reproducibility
LLM_MAX_TOKENS=8192
```

Documentation defaults to Claude Sonnet but explicitly supports OpenAI (`openai/gpt-4.1`), Vertex (`vertex/gemini-2.5-pro`), and local Ollama. Mastra's model router handles each.

## SDD/TDD Gates

Enforced in `pnpm verify`:

1. **`pnpm spec-check`** — for each package, `docs/specs/<pkg>.md` must have a newer mtime than the latest `src/**` change. Fails CI otherwise. Generated by `pnpm spec:touch` after editing a spec.
2. **`pnpm test`** — Vitest must pass.
3. **`pnpm typecheck`** — `tsc --noEmit` clean.
4. **`pnpm lint`** — ESLint clean.
5. **`pnpm mock:test`** — mock-adt-server passes its captured-response tests.
6. **`pnpm bench:smoke`** — runs one scenario with one tool against the mock to prove end-to-end wiring.
7. **PR template** requires a changeset (`pnpm changeset`) following the changesets pattern.

`pnpm verify` is the single gate. PRs can't merge without it.

## Risks & mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| `abapify/adt-cli` cold-start `npx` latency dominates wall-time | medium | high | CI installs CLI globally (`npm i -g`); first smoke run will measure; documented in results |
| `mastracode` 0.22 API changes | medium | medium | Pin version; interface boundary in `harness` is the abstraction |
| arc-1 install requires license / specific BTP creds | low | low | Runs against mock — no creds needed; `--url http://127.0.0.1:8080` |
| arc-1 deliberately hides SAP XML internals → "did the agent actually understand the error?" is hard to grade | medium | medium | Transcript-level grader (`abap-eval-grader` skill) reads tool-call arguments/results, not just the final outcome |
| ADT XML namespaces drift across SAP versions | low | low | Lock the namespace map to v2/v1; document mismatches as known issues |
| LLM nondeterminism ruins reproducibility | medium | medium | Temperature 0, per-run seed, multi-trial flag (v1.1), report std |
| Nx + pnpm + TS path aliases fighting | medium | low | Use Nx's `tsconfig.base.json` extension once; do not fight it |
